# Plan

The plan is the deliverable, and this playbook implements nothing.

- **Before** "Settle open questions by prototype before you write": choose the target by the Architecture decisions section below when the plan picks an API or architecture target. When the plan changes a public API, that runs `pstack:architect` for the comparison (reviews: api-plan), then the panel on the finished plan, and records the panel's challenge delta. A row that breaks a public API names its callers, `www` docs, kitcn skill references, templates, examples and proof. A removal that neither the owner's request, a Pursue verdict this plan continues nor `VISION.md` clears becomes a verdict item when the plan is written, as the Hard cut section of `.agents/playbooks/references/architecture.md` says.
- **Replace** "Copy the skeleton below into the plan file and fill every placeholder": write `docs/plans/<date>-<slug>.md`, or `docs/plans/<issue>-<slug>.md` for an issue, with one authoritative `Status:` line and a `Playbook: plan` line under it, so its page leads with the sections this file's frontmatter names. A plan built from a `docs/prds/**` PRD or a `docs/milestones/**` rung links it as its source and keeps its task packets as steps. An architecture or API adoption plan reads `.agents/playbooks/references/architecture.md` in full, keeps its decision ledger, and writes the Page sections it names that apply, starting with `## Prior art`. A plan whose change readers can see in `www`, such as a public API, CLI command, plugin or scaffold, names each affected `www` page and its matching `packages/kitcn/skills/kitcn/**` reference, and gives each pair one step. A plan that changes a package names its changeset step, and one that changes a template or scaffold names its `bun run fixtures:sync` and `bun run fixtures:check` step. Every plan has `Status:`, Outcome, Scope, Decisions with their reasons, Steps as `- [ ]` boxes that each name the proof closing them, and Proof, plus the `Defaults` and `Open questions` sections from `AGENTS.md`'s Plan pages when it has any. Before writing any step's proof or phase exit, load `verify` through the Skill tool; reading its references does not count, because the skill decides what proves a runtime, CLI or browser claim.
- **Replace** "Run `node skills/poteto-mode/scripts/check-plan.mjs <plan.md>`": check an architecture or API plan against the architecture reference's Ready list, or for another plan, that every step names its proof and no decision-changing question is left. A plan with a Start Gates table is ready only when every row resolves Applies and records its evidence or the reason it does not apply. A Start gate on another plan's work records that work's own check run at `HEAD`, never that plan's `Status:` line. Completion Gates resolve at Done, when no row is pending. Load `verify` through the Skill tool before running base controls. Before the plan goes on to its build, run each step's cheapest control at base in a detached worktree, such as the half of its proof that must fail at `HEAD` or a delete-and-typecheck spike. Rewrite any step whose control does not behave as the step claims, because a citation proves only that its line exists.
- **Replace** "Write under `/technical-writing` in full, then `/unslop`": write the plan with `pstack:technical-writing` as a reference, then run one `unslop` pass, per `AGENTS.md`'s Writing passes rule. The body is one Diátaxis mode, how-to; appendices hold explanation and reference.
- **In** "Hand back. Post the plan path": the plan names the Build playbook as its execution playbook. When a panel reviews the plan, its intent names as an invariant to attack that each phase beats keeping the incumbent plus the earlier phases, so a finding that a phase should not be built is in scope, and the plan records the challenge delta. Then publish the page per `AGENTS.md`'s Plan pages. A request for only a plan, such as "plan" or `plan <goal>`, ends there. Any other route, such as a Pursue verdict, runs Build, as the Autopilot rule says, unless an open question stops the run or the user said "stop at plan". After a stop, "go" accepts every default and runs Build. The page lists every claim made to the user in conversation that the plan reverses, such as which packages or entries it changes.

## Architecture decisions

State the ideal target before compatibility or current plans constrain it. Compare at least two materially different targets, which differ in ownership, lifetime, data model, public call shape, import graph or runtime strategy; renames and wrapper reshuffles do not count. Ground the comparison in how the libraries `VISION.md` names, such as Drizzle, tRPC, TanStack Query, better-auth and shadcn, solve the same job, read from their local clones in `..`. A target that grows what a Convex function entry statically imports loses to one that keeps it per module or behind a plugin unless the plan shows the cost is worth it. A plan that changes a public API runs `pstack:architect` for the comparison (reviews: api-plan), and its first design pass is always architect's arena, with independent runners and a cross-judge; another architecture plan runs `pstack:architect` only where pstack's own trigger calls for it, such as code that crosses a function boundary, and otherwise compares its targets in the lead's own table, records its must-answer questions in the plan and runs their probes before it picks the target. When a panel reviews the finished plan, it attacks the winner, and the plan replays architect once only when that attack improves or replaces it. When architect runs, no build brief goes out until its judge has picked the base and grafts. The runner task and the judge's rubric state the outcome the design must reach, never the mechanism, and the comparison includes one candidate or stated control that adds no new artifact. Before grafting, list each case a losing candidate handles that the base drops, such as an action context, a live subscription or a scaffold variant, and make each one a graft or a named limit of the plan before the panel. Prove each premise of the base and its grafts that existing code already does something with `pstack:blast-radius`'s run-it step, because a judge's verified citation proves only that the line exists. Every open question or "not verified" flag about a path the target removes goes into the arena prompt as a must-answer item and runs as a probe before the pick, never as a build step. After a panel or verification cut, re-score the surviving synthesis against the incumbent in the comparison table; when the margin is gone, keep the incumbent or rerun the arena. Record the challenge delta in the plan: `unchanged`, `improved` with what was deleted, merged, moved or re-owned, or `replaced` with the rejected target, the new target and the decisive evidence. Every removed export, adapter, owner or public noun names the behavior it carried, its replacement or proven redundancy, and its regression proof. Redundancy is proven by running the removed path and its replacement on the same input; a typecheck proves only that callers compile. Adopt in at most three phases, each independently valuable and ending with a keep, revert or quarantine decision. Compatibility and difficulty change phase order, never the target. Log a change made after the user's approval, or to the arena's picked base or grafts after its verdict, as the agent's own call in a deviation row, and name it in the panel brief as a decision to attack.
