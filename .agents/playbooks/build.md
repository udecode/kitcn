# Build

"go" runs every slice of the accepted plan without pausing between slices. This playbook applies to a plan that goes on to its build, to "go" on an accepted plan and to a hard cut; an ad hoc cleanup follows `refactoring.md` alone. The plan already settled the design, so the build does not reopen it. The todo list names this playbook on its first line, so a resume after compaction reloads it.

- **Replace** "`how` over the affected subsystem": reread the plan and the current source, repair stale claims first, and record the execution authority in the plan. Reproduce each planned guard's or refusal's state through the public entry before building it, because a validator or an earlier owner can already rule it out. Log an unreachable one as a deviation instead of building it. A planned check that already fails at the build base, run in a detached worktree, lands with a shrink-only baseline that names each current violation and its owner, and is never dropped. A baseline captured mid-build can hold the build's own regressions, so a "no new finding" proof against it counts as partial. Copy every Before and After gate below that the plan triggers into the plan's Completion Gates table with a pending cell, and replace each cell with the gate's artifact or `skip: <reason>`. A plan whose `Status:` is Done, that only settles a design, or that another plan replaces does not build: name the plan that owns the work now and build that one, recorded as a Defaults row.
- **Replace** "`architect` for parallel design exploration": skip, because the plan's target already passed the Plan playbook's Architecture decisions. A slice that cannot follow the plan goes back to the Plan playbook, which revises the plan and builds on in the same run. Reversing an approved gate's verdict is such a slice; the lead logs it as a deviation row, takes the better-evidenced verdict and keeps the other as a saved patch. Doing less than a slice approved continues with a deviation row only when the rest is unreachable or disproven; the time or effort left never shrinks a slice and is never a reason to ask. A changed or dropped approved proof becomes a `look` Defaults row with a saved patch and the word that reverses it. A substituted mechanism or a reverted step is a deviation row. A replacement goes back to the Plan playbook as a plan revision, so the Review rule's re-review applies to it.
- **Before** "Delegate code-writing to a subagent": when the plan changes a public API, run `pstack:blast-radius` on the change first, so callers outside the plan's sweep, such as templates, the example app and docs, are known before code moves.
- **In** "Delegate code-writing to a subagent": hand the plan's slices to delegates in order. Before briefing or running a step, load every skill the step or its gate names, such as `verify` before the first proof gate and `changeset` before a package slice closes. A load from before a compaction or for an earlier plan does not count. Each brief asks for focused proof first and surgical edits, live behavior in `pstack:tdd`'s red-green cadence and no test that only asserts removed code stays removed. The lead ports every shared-primitive improvement to all its consumers and verifies each.
- **After** "Verify on the matching surface": hard-cut the rejected APIs per the Hard cut section of `.agents/playbooks/references/architecture.md` and sweep callers, exports, tests, templates, the example app, `www` docs and the kitcn skill references. The plan stays open while any of them still teaches the rejected shape.
- **After** "Verify on the matching surface": a change readers can see updates its `www` pages to the latest state only, with no changelog wording, and the matching `packages/kitcn/skills/kitcn/**` reference in the same diff, per that skill's `references/setup/doc-guidelines.md`. A plugin API change also updates `references/features/create-plugins.md`. Then run `bun tooling/sync-kitcn-skill.ts`, `bunx intent validate skills` and `bunx intent stale`.
- **After** "Verify on the matching surface": a package slice runs `bun --cwd packages/kitcn build` and writes or updates its changeset per `changeset`. A `kitcn init -t` template or scaffold slice runs `bun run fixtures:sync` then `bun run fixtures:check`, and its runtime proof runs on a prepared scenario through `verify`. A slice that changes what a Convex function entry statically imports names each import the entry gains or loses in the plan's Completion Gates table.
- **After** "Verify on the matching surface": before any expensive acceptance run, such as `bun check`, `bun run test:runtime` or a scenario matrix, run `bun typecheck`, the focused tests and `bun lint` on the slice's files. Each can still force a code change, and a code change reopens that run.
- **After** "Verify on the matching surface": every slice that touches code shared across packages, plugins or entries, the last one included, runs `pstack:thermos` on its diff before the next slice, or before the close's writing passes and panel. The brief names the plan, so a breakage the plan approves, such as a hard cut, counts as intended, and tells `thermo-nuclear-review` to skip its PR-discussion step, because a slice is not a PR. A build skips this review when, at its first slice, a reviews row such as `api-build` or `push`, or the owner's request, already owes a panel on its diff, because every panel seat applies both lenses. Its reviewers run as fresh-context subagents, never inline on the lead's own diff. The split law in `.agents/playbooks/refactoring.md` overrides its size-based split advice. A finding on a defect the slice introduced gets fixed in that slice; a finding on deferred or pre-existing code goes to Open work with its `owner:`.
- Before a panel reviews the diff, run `bun lint` on the task's files without fixing, so a lint rule cannot force an edit after the panel has reviewed the diff. `bun lint:fix` stays the last check that edits code.
- A panel fix lands its cheap reproduction as a test in the task's diff in the same round, so the next round reviews it.
- A panel fix that replaces a mechanism's approach revises the plan's step and Defaults in the same plan file. The Verdict playbook runs first when the mechanism is a kitcn API or architecture, and the lead revises the plan from its verdict. When the verdict rejects the replacement, the lead does not build it; it reverts the defective code to its state before this plan iteration changed it and narrows the claim with a report. When the goal still needs the mechanism, the new plan iteration that rebuilds it runs the Verdict playbook first and gets its own panel, because that exit is the growing workaround chain the Bug fix playbook's Pokayoke names.
- A `/pstack:correct` change made during a build is its own change with its own review. A feature round's warning on it, or on pre-existing code outside the plan's steps, is deferred with its `owner:`.
- **Replace** "Rebase into small, ordered commits": land the build through `node .agents/pstack/land.mjs`, which squashes it into one commit, per `AGENTS.md`'s Delivery rule. A plan that says each of its phases lands as its own commit lands each phase this way, all in one session, as `.agents/pstack/rules/long-runs.md` says, and only the last phase runs the close below.
- **Replace** "Run **Opening a PR**": when the reviews list names the work or the user asked for one, run its panel on the diff before landing. `land.mjs` pushes the commit or opens its PR, as the clone's `pstack.delivery` setting says.
- A plan whose slices preserve behavior runs each slice under `refactoring.md`'s packet law, with the plan's slices as its steps; this playbook's close still applies.
- At the close, record the evidence and the plan's status: completing a design does not complete adoption. Finish the plan's `## Close`, evidence, file and line references and writing passes, then, when the reviews list names the work or the user asked for one, its panel on the diff. A durable decision the build settled goes to its owner, `VISION.md` for doctrine and `docs/adr/**` for a technical decision, as `docs/README.md` says. Before the last land, the plan writes its own `Public API` and `Main changes`, per the `plan-page` skill; then the close edit that `.agents/pstack/rules/land.md`'s Landing names sets the plan's ticks and `Status:`, so the landing commit includes them. After it lands, republish the page. Every build then runs `.agents/pstack/rules/chips.md`'s Close, which cards the run's own Ready offers and runs no sweep, and ends with the page link, that Close's line and its commits. Stop there.
