# Bug fix

- **Before** "Reproduce it yourself on the matching surface via the driver skill": a udecode/kitcn issue is read through `gh` with its comments as the report. Any comment, label or close on it follows `.agents/pstack/rules/messages.md`.
- **In** "Reproduce it yourself on the matching surface via the driver skill": attached screenshots and recordings are the report; transcribe a recording with `video-transcripts` and keep the reporter's exact setup, call, command and expected result. Reproduce at the layer the reporter hit, through `verify`: a focused test for package behavior, the `kitcn` command and its `--json` output for the CLI, and a prepared scenario for scaffold, codegen, auth or runtime behavior, never a committed fixture run in place. "Regression" means reproducing at the last release tag, such as `kitcn@0.33.12`, or the commit the reporter names, in a detached worktree as the baseline, then on the current checkout, and naming the change that broke it.
- **In** "Binary-search the cause": before the first hypothesis, search `docs/solutions/**` for a failure already diagnosed there. Tighten the loop first, to seconds rather than minutes, asserting the specific symptom, with time pinned and randomness seeded; raise a flaky bug's reproduction rate until it can be debugged, and rule out cross-file test contamination with `verify`'s testing reference first. Each hypothesis states a falsifiable prediction ("if X is the cause, changing Y makes the bug disappear"), and each probe tests one prediction by changing one variable at a time with targeted boundary logs, never log-everything. A cause in Convex, better-auth or another dependency is read from its local clone in `..`. Once the cause is confirmed, find the landed commit that introduced it with `git log -L`, `git blame` or `git bisect`. A blamed line alone is a suspect, not the cause. Read that commit's diff against the cause, and when the diff does not make it plain, check that the bug reproduces at that commit and not at its parent. The fix's commit message names that commit as `Introduced-by: <sha>`, with one line for each commit when several did, because `land.mjs` refuses a `fix` commit without the line. Code that was broken when it landed names the commit that landed it. Only a cause older than the history or outside the repository, such as a dependency, says `Introduced-by: none`.
- **After** "Binary-search the cause": `diagnose` stops here with the cause, its evidence and the commit that introduced it.
- **In** "Plan the fix": fix at the owning layer: the package or runtime that owns the behavior, as `VISION.md` says. A wrong scaffold or codegen output is fixed in its template or generator and regenerated, never in the example or fixture output. Repair the violated invariant and what let it escape, per Pokayoke below, never with a caller workaround. The same value added at many callers only to fill a required input is that workaround, so decide at the owning API, through the Verdict playbook, whether the input should be required. A fix that adds a static import to code a Convex function entry loads keeps that entry's import graph narrow, as `AGENTS.md`'s bundle-size rule says.
- **After** "Verify on the same surface": a fix already reported as done, locally or publicly, that then fails its exact replay or final verification, or that the reporter contradicts, is a failed fix; the expected red before a fix is not one. The reporter assertion must run before a failure counts: a proof host that fails before the assertion, such as a local Convex backend that never boots, is repaired at its own owner, and the same product attempt restarts. Before another product attempt, revoke the earlier green and completion claims, leaving public corrections to the owner. Freeze the product bytes, rerun the failing assertion and name what made it red: product nondeterminism, host readiness, test contamination or a stale prepared scenario. Name why the earlier proof passed (the invariant, the test boundary, the runner or the served build) and repair that gap at its owner, preferring an assertion that rejects the escaped case over new instructions. Then restart from exact reproduction with every still-applicable acceptance item. On the second failed fix, or at once when the fix compensates across layers or patches generated output, run `pstack:recall` on the bug and its owner with no time window, then run the Verdict playbook on the owner before another attempt, with the recall brief as its history. The review compares deleting or merging the implicated owners before adding compensation.
- **After** "Verify on the same surface": tag every debug probe with a unique prefix, then grep-remove them all and delete throwaway harnesses before done. A package edit runs `bun --cwd packages/kitcn build` and needs its changeset per `changeset`; a template or scaffold edit runs `bun run fixtures:sync` then `bun run fixtures:check`.
- **Replace** "Stage the commits so the failing repro lands before the fix": a test written first, in `pstack:tdd`'s red-green cadence, lands together with the fix, never as a failing commit of its own, per `AGENTS.md`'s Tests rule; `land.mjs` squashes the test and the fix into one commit, per the Delivery rule.
- **Replace** "Run **Opening a PR**": when the reviews list names the work or the user asked for one, run its panel on the diff before landing. `land.mjs` pushes the commit or opens its PR, as the clone's `pstack.delivery` setting says.
- **Redesign runs.** When the design is the cause of a bug, the run redesigns it as early as the evidence allows and still lands code in pieces, instead of patching one case after another. More than one failure kind with the same owner, shown by its tests, scenarios, repros or the review of one fix, counts as the second failed fix, so the failed-fix review above runs at once. After that review the run is a redesign run, whatever its verdict. A run the owner's own words start as a redesign is one too.
  1. **Write the expected results first.** List each case the owner must handle as a row: the input, such as a procedure call, a schema, a config or a CLI invocation, the steps in order and the result that must follow. Build the rows from the failing tests and scenarios, every reported repro and the findings of earlier plans. Every row gets a result. Where no law decides one, the lead picks it as a `look` Defaults row with the word that reverses it. A result that removes current behavior follows the architecture reference's Hard cut. Rank each row P0, P1 or P2 by chips.md's Priority. The table lives in the run's plan.
  2. **Test against the table.** Each row the run makes pass names the suite test or scenario that covers it, and the table records each row that still fails.
  3. **Design once against every P0 and P1 row.** `architect` runs on the whole table. The design lists its slices in landing order, and each slice is code the finished design keeps. The plan gets a panel before its first slice is built.
  4. **Land each slice when it is ready.** A slice lands through `land.mjs` when it fixes at least one failing P0 or P1 row, or completes a behavior-preserving step the design lists for one, breaks no passing row, passes the suite and clears the panel the reviews list's `push` row calls for.
  5. **Turn each review finding into a row**, and run the table's tests again. A finding the finished design cannot meet on a P0 or P1 row pivots the run, as the Autopilot rule says.
  The run is done when every P0 and P1 row passes, and each failing P2 row goes to the plan's Open work.
- A fix for a udecode/kitcn issue closes with its evidence packet: the classification and root cause; the reporter's exact steps, setup and expected result; the owner and files; the exact red proof; the final local ref; the scenario, CLI or runtime proof or its limitation; the changeset status; the pstack block's Review result or N/A; and the unresolved caveat. Public wording claims only what the packet proves.
- **Pokayoke.** Repair the violated invariant and the mechanism that let it escape. Prefer one canonical owner, an impossible invalid state, or a reusable assertion over caller workarounds and more instructions. This playbook owns the focused repair and failed-fix recovery; `verify` owns evidence. A recurring invariant failure or growing workaround chain triggers the Verdict playbook before another fix. A green proxy never closes a failing or unexecuted reporter interaction. One confirmed violation opens an audit of its whole governed area beyond the current diff, package or directory: record the exact rule and enumerate every applicable file, consumer, template and parallel implementation before calling that audit complete. Read each candidate in context, because a similar spelling does not prove the same defect, and fix every confirmed instance the request authorizes repairing. A compliance claim covers only the files enumerated and read; a clean sample or grep does not prove the governed set complies.
- **Blockers with a working reference.** Before declaring an environment, deployment, provider or missing-input blocker on a path that has a reportedly working reference, trace that reference operation through its caller, effective configuration, request, response and result, and compare the target at the same boundaries. One rejected request does not prove the deployment, account or integration unusable. Withdraw an overbroad blocker in the active plan as soon as contrary evidence appears, keep the original failure and the next executable check, and continue independent authorized work.
