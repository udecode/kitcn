# Babysit

It finishes started work and never starts the next feature.

- **Before** "Declare the mode and resolve the forge before any poll": "review PR <number or URL>" on someone else's PR is review-only (reviews: external-pr). Run the panel on its diff, briefed with the PR body, its linked issue and any plan it carries in `docs/plans`, and have it judge whether the change should exist, whether its design is right, and the code. Return the findings in the reply and stop. The run keeps no plan, page or decision log, and it makes no edits, commits, pushes, replies or review submissions.
- **Before** "Declare the mode and resolve the forge before any poll": resolve the candidate, either a PR's diff, body, checks and review threads through `gh`, or the current worktree's change. Lead with a candid verdict on whether the change should exist and its strongest justified cut, running the [Verdict playbook](./verdict.md) when an API or architecture decision changes that verdict. Repair what the verdict keeps at its owner (the Bug fix playbook for a defect, the Refactoring playbook for code shape), so callers, exports, `www` docs, the `packages/kitcn/skills/kitcn` references, scaffold templates and the fixtures they regenerate, and changesets end coherent, and prove it with `verify`. For a PR you opened, write its description and history with `make-pr-easy-to-review`. On another person's PR, leave their description and history alone and keep one comment about your commits, as the `plan-page` skill's PR section says. The current worktree skips the Babysit steps, except the code-quality review below, which it runs before it calls the tree clean. On any PR, commit the repair and push it to the PR's head branch without asking, under `AGENTS.md`'s Delivery rule, unless that branch is `main`. The run merges that PR once it is green, as the merge bullet below says. Any other PR comment, thread replies, closing and history rewrites each need the owner's word for that action, because this repository is public and a PR's author may be outside the team. Until then, the thread replies the steps below prepare stay drafts, and the run does not wait for them.
- **Releases.** Two merges publish to npm: the `changeset-release/main` PR, titled "[Release] Version packages", and any PR whose `auto-release` block in its body is checked, which the Changeset auto-release workflow checks by default for a patch changeset. A release waits for the owner under the Autopilot rule, so the run merges such a PR only when the owner's request names the release. Otherwise a babysit of the release PR runs `check` only, and any other such PR stops green before the merge with the checked box named under Needs you. A rewritten PR body keeps the `auto-release` block as the workflow wrote it.
- **Plan page.** A PR babysit that repairs the PR, unlike the review-only one above, keeps its plan and decision log in `docs/plans` and publishes the plan page before the first review round.
- When PR feedback states an objective, low-ambiguity rule, treat it as a confirmed rule violation and run the Bug fix playbook's Pokayoke audit of its whole governed area, decide the ambiguous instances once, and report those extra fixes apart from the comment you answered. A taste or architecture comment gets one decision or a pushback draft; one that changes a reusable public API goes to the Verdict playbook.
- **Before** "Stop at the human's line": before calling a PR ready, run `pstack:thermo-nuclear-code-quality-review` on its diff, with the split law in `.agents/playbooks/refactoring.md` overriding its size-based split advice. Fix or answer every finding on a defect the candidate introduced, wherever that defect sits, such as a helper its change left without callers. A finding on code it neither changes nor breaks goes to the plan's Open work with its `owner:`, or to the reply when the run keeps no plan.
- **Before** "Stop at the human's line": every PR babysit except the review-only one and those the Releases bullet holds runs `drive` and then merges, because "babysit" is the owner's word to merge. It replaces Shipping for that PR. A merge into `main` is that word for the push, so the Autopilot rule's stop for a push to `main` does not hold it. A draft does not stop it either; run `gh pr ready <number>` once the PR is green. The run stops before the merge only when the verdict cuts or rejects the change, a call has no clear pick and cannot be undone, a repair cannot reach the PR's branch, or the merge would release. First read the signed-in user with `gh api user --jq .login`. The method is `--squash`, as this repository's merges are.
  - For `zbeyens`, a missing approval never blocks. Drive until no check is pending or failed and the watcher names no blocker other than `review-required` or the draft state, then run `gh pr merge <number> --squash --admin --match-head-commit <headRefOid>`. Read back `gh pr view <number> --json state,mergedAt,baseRefName` and confirm the merge commit is on `main`. A failed check goes back through `drive` to be fixed and is never merged over.
  - For any other user, once the watcher's only blocker is `review-required`, run `gh pr merge <number> --squash --auto` and stop. The PR merges when a reviewer approves its latest push.

## Current-tree closure

Clean means:

- no verified in-scope finding remains unresolved, and structured review passed or is recorded as not applicable;
- every accepted code-shape finding (shallow modules, over-splits, fake wrappers, ownership confusion, duplicated helpers, navigation friction) is fixed through the Refactoring playbook, rejected, or routed with owner and reason;
- the coherence audit found no stale dirty fix, fake alias, compatibility shim, docs and API mismatch, orphan test, hand-edited fixture or generated file, weak command, missing changeset where a package changed, or new static import that pulls code into a Convex function entry that does not use it;
- when the diff materially changes public API, the Verdict playbook judged the change and every P0 and P1 finding is resolved or explicitly rejected;
- required focused proof after the last patch passes or is explicitly N/A;
- generated outputs affected by the diff are regenerated from their source (`bun run fixtures:sync` then `bun run fixtures:check` for scaffolds, `bun tooling/sync-kitcn-skill.ts` for the repo-local kitcn skill) or intentionally absent;
- `www` docs describe only the latest state and match the kitcn skill references, and API, examples and tests are coherent with current source;
- no dirty speculative half-patch remains;
- the files called clean are in the current checkout; a captured PR or range diff is not current-tree clean until applied and verified here.

Clean is a recorded state that meets every line above; one terse review does not make a tree clean.

Review comments become sweeps only where they generalize: prefer one coherent follow-up refactor over many tiny copy-paste fixes, keep the blast radius proportional to confidence, and call out a sweep that depends on another PR. Naming preferences, broad architecture changes without repo evidence, weakly general style choices, public API widened for local convenience, and anything that cannot be explained in one sentence are not sweep targets. An outdated review thread is not stale by default: `isOutdated` means the hunk moved, so relocate the concern by source text, path and surrounding code before deciding.
